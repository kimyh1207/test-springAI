# 21-2. 기술 의사결정 기록(ADR)과 회고

## ADR이란

ADR(Architecture Decision Record)은 "왜 이 기술을 선택했는가"를 기록하는 짧은 문서다. 6개월 후 팀에 합류한 사람이 "왜 FastMCP를 썼지?"라고 물었을 때 답이 있는 문서다.

---

## ADR 템플릿

```markdown
# ADR-001: MCP를 도구 통합 표준으로 채택

**날짜:** 2025-06-01  
**상태:** 채택됨  
**결정자:** vivace

## 컨텍스트

AI 에이전트가 주문 DB, 상품 검색, 정책 RAG, 쿠폰 시스템 등 여러 외부 시스템을 호출해야 한다.
각 시스템을 모델별로 별도 구현하면 Claude, GPT-4o 등 모델을 교체할 때마다 전체 도구 코드를 다시 작성해야 한다.

## 선택지

1. **직접 함수 구현**: Claude tool_use 스키마에 맞춰 직접 정의
2. **LangChain Tools**: @tool 데코레이터, LangChain 생태계에 종속
3. **MCP (채택)**: Anthropic 공개 표준, 모델 독립적

## 결정

MCP를 선택한다.

**이유:**
- 도구를 한 번 만들면 Claude Desktop, API, 향후 다른 MCP 클라이언트에서 재사용 가능
- JSON-RPC 기반 표준 — 모델이 바뀌어도 서버 코드 수정 불필요
- FastMCP로 보일러플레이트 최소화

## 트레이드오프

- MCP SDK 성숙도가 아직 낮음 (2025년 기준 v1.x)
- stdio 기반 로컬 실행은 원격 배포 시 SSE로 전환 필요

## 결과

도구 5개를 MCP 서버로 구현, Claude Desktop과 API 클라이언트 모두에서 동일 코드로 동작 확인.
```

## 프로젝트 ADR 모음

```markdown
# ADR-002: 벡터 DB로 Chroma 선택 (pgvector 대신)

**날짜:** 2025-06-03  
**상태:** 채택됨

## 컨텍스트
정책 문서 RAG를 위한 벡터 DB 필요.

## 선택지
1. **pgvector**: 기존 PostgreSQL에 확장, 인프라 추가 불필요
2. **Chroma (채택)**: 독립 설치, Python SDK 우수
3. **Pinecone**: 관리형 서비스, 비용 발생

## 결정
Chroma 선택.

**이유:**
- 로컬 개발 시 별도 서버 없이 `PersistentClient`로 사용 가능
- LangChain 공식 지원, 예제 풍부
- 프로덕션에서 문서 수 < 10만 건이므로 pgvector 수준의 성능 불필요

## 향후 재검토 시점
문서가 100만 건을 넘거나, 기존 PostgreSQL 팀이 합류하면 pgvector 마이그레이션 고려.
```

```markdown
# ADR-003: Spring Boot를 API 게이트웨이로 사용

**날짜:** 2025-06-05  
**상태:** 채택됨

## 컨텍스트
인증, 속도 제한, 캐싱을 처리할 레이어 필요.
AI 레이어(FastAPI)는 Python 생태계에서 분리하고 싶음.

## 결정
Spring Boot를 게이트웨이로 사용, FastAPI는 내부 AI 서비스로 분리.

**이유:**
- Spring Security로 JWT 인증 검증이 성숙함
- Spring Cache + Redis 연동 간단
- 팀 내 Java 경험자 존재

## 트레이드오프
두 언어 유지 비용. 단일 언어(Python FastAPI만)로 구성하는 것도 가능했으나
인증/보안 기능의 안정성을 위해 Spring 선택.
```

## 회고 작성법

회고는 "잘된 것 / 아쉬운 것 / 다음에 다르게 할 것" 3단 구조로 쓴다.

```markdown
# 캡스톤 프로젝트 회고 — 이커머스 AI 에이전트

**기간:** 2025년 6월 1-30일  
**작성자:** vivace

## 잘된 것

**MCP 도구 설계**
도구 경계를 명확히 나눠서 각 도구가 단일 책임을 갖게 했다.
덕분에 RAG 도구만 교체해도 에이전트 코드를 건드릴 필요가 없었다.

**테스트를 먼저 짠 것**
MCP 도구 → 에이전트 순서로 테스트를 먼저 작성했더니
통합 후 버그가 거의 없었다.

**비용 추적 초반부터 구현**
일별 비용을 처음부터 추적했기 때문에
$50 한도를 실제로 넘기 전에 캐싱으로 절감할 수 있었다.

## 아쉬운 것

**RAG 청크 크기 튜닝 시간 과소 평가**
처음에 청크 500자로 설정했다가 "반품 기간이 얼마나"라는 질문에
엉뚱한 배송 정책을 가져오는 문제가 발생했다.
오버랩 설정과 메타데이터 필터를 추가하는 데 이틀 소요.

**세션 관리 설계 후반**
멀티턴 세션을 처음에 설계에 넣지 않아서
에이전트 구현 후반에 추가하면서 코드가 복잡해졌다.

## 다음에 다르게 할 것

1. **설계 단계에서 세션 관리 포함**: 데이터 흐름 설계 시 세션 ID 처리를 먼저 정의
2. **RAG 품질 자동 평가 먼저**: RAGAS 평가를 인덱싱 직후에 실행해서
   청크 크기 결정에 데이터 기반으로 접근
3. **모델 비용 계획**: 프로젝트 초반에 예상 트래픽 × 모델별 단가를 계산해서
   모델 선택에 반영

## 수치 결과

| 지표 | 목표 | 실제 |
|------|------|------|
| 에이전트 정확도 | ≥ 80% | 84% |
| P95 응답 시간 | < 3초 | 2.1초 |
| 일일 비용 | < $10 | $3-5 |
| 테스트 커버리지 | ≥ 80% | 82% |
```

## 기술 면접에서 ADR 활용

```
면접관: "왜 LangChain 대신 MCP를 선택했나요?"

나쁜 답: "최신 기술이라서요."

좋은 답: "LangChain도 검토했는데, 저는 특정 프레임워크에 종속되지 않는
          도구 표준이 필요했습니다. MCP는 JSON-RPC 기반 공개 표준이라서
          나중에 모델을 GPT-4o로 교체해도 서버 코드를 그대로 쓸 수 있었습니다.
          실제로 ADR에 두 선택지를 비교해뒀고, 트레이드오프도 문서화했습니다."
```

> "ADR은 과거의 나에게 보내는 편지다 — 왜 그 결정을 내렸는지 기록하지 않으면 6개월 후 다시 같은 고민을 반복한다."
